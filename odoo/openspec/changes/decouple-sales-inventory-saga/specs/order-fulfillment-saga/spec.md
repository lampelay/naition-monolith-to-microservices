# Spec Delta

## Purpose

Определяет поведение исполнения заказа через распределённую сагу: оптимистичное подтверждение, асинхронное выделение из запасов, replenishment-ветку по закупке, exception-обработка и гарантийные свойства (идемпотентность, подвешивание вместо ложной компенсации).

## ADDED Requirements

### Requirement: Оптимистичное подтверждение заказа
Система SHALL подтверждать заказ (переход в состояние продажи) в транзакции только своего домена и SHALL публиковать событие подтверждения через outbox; подтверждение НЕ SHALL ждать выделения запасов, создания складских документов и НЕ SHALL отказывать из-за отсутствия товара на складе.

#### Scenario: Подтверждение при недоступном сервисе запасов
- **WHEN** подтверждение заказа, а сервис запасов недоступен
- **THEN** заказ подтверждён, сага исполнения создана и ожидает (pending), пользователь не получил ошибку

#### Scenario: Нехватка не блокирует подтверждение
- **WHEN** подтверждение заказа по SKU с нулевым свободным остатком
- **THEN** заказ подтверждён, дефицит становится виден асинхронно как shortage-статус строк

### Requirement: Статус выделения на заказе
Система SHALL поддерживать на каждой строке заказа наблюдаемый статус выделения (awaiting / allocated / partial / shortage / expired-exception), обновляемый событиями запаса монотонно по seq; статус SHALL быть доступен UI и биллингу как проекция, без прямых запросов к данным запасов.

#### Scenario: Статус по событию
- **WHEN** получено PromiseCreated по строке
- **THEN** статус строки allocated; при DeliveryValidated с неполным фактом — partial

#### Scenario: Повторная доставка старого события
- **WHEN** событие со seq ниже уже применённого
- **THEN** статус не изменяется (защита от перестановки доставки)

### Requirement: Жизненный цикл саги и политика отгрузки
Сага SHALL создаваться на подтверждение заказа (instance = заказ) и проходить состояния: awaiting_allocation → allocated → planned → shipping → delivered → closed, с exception-состояниями shortage_replenishment и EXCEPTION_WAITING; политика «всё сразу» SHALL ждать выделения всех строк, политика «частями» SHALL разрешать отгрузку по готовым строкам.

#### Scenario: Политика «частями»
- **WHEN** из трёх строк выделены две
- **THEN** план отгрузки допустим по выделенным строкам, третья остаётся awaiting/shortage

#### Scenario: Политика «всё сразу»
- **WHEN** из трёх строк выделены две
- **THEN** сага не переходит в planned до выделения третьей или явного изменения политики/строк

### Requirement: Replenishment-ветка через закупку
При shortage строки, допускающем закупку по складской buy-цепочке, сага SHALL выдать команду ReplenishRequested legacy-адаптеру, дождаться POAccepted, затем GoodsReceived и инициировать повторное обещание; отмена этой ветки SHALL компенсироваться уменьшением количества строки PO (POLineDecrease), но не отменой PO целиком.

#### Scenario: Счастливая ветка закупки
- **WHEN** shortage → PO принят → приход на склад qty, покрывающий дефицит
- **THEN** сага запрашивает повторное обещание, при успехе следует к planned

#### Scenario: Заказ отменён до прихода
- **WHEN** отмена заказа в состоянии shortage_replenishment с активным PO
- **THEN** опубликован POLineDecrease по незакрытым строкам, PO остаётся живым для других заказов

#### Scenario: Закупка вне пути (нет поставщика/политики)
- **WHEN** shortage по строке без buy-цепочки
- **THEN** сага уходит в EXCEPTION_WAITING без команды закупки

### Requirement: Exception-ветка без автотмены
Нехватка, истечение обещания и таймаут ветки SHALL переводить сагу в EXCEPTION_WAITING (долгое состояние для ручного разрешения) и SHALL уведомлять ответственного; система НЕ SHALL автоматически отменять заказ ни по одному из этих триггеров.

#### Scenario: Истечение TTL обещания
- **WHEN** PromiseExpired по строке выделенного заказа
- **THEN** сага в EXCEPTION_WAITING по строке, заказ сохраняет состояние продажи, уведомление создано

### Requirement: Гонка изменения подтверждённого заказа
Уменьшение количества строки подтверждённого заказа SHALL проверять предельное потребление через синхронную условную команду к сервису запасов (факт потреблённого обещания), а не только по локальной проекции отгрузок; при new_qty < потреблённого изменение отклоняется.

#### Scenario: Проекция отстаёт, факт опережает
- **WHEN** уменьшение количества ниже qty_delivered по проекции, которая ещё не получила последний DeliveryValidated
- **THEN** команда проверки к запасу возвращает потреблённое больше нового количества, изменение отклонено с явной ошибкой

### Requirement: Подвешивание вместо компенсации при отказе запаса
При недоступности или fail-closed состоянии сервиса запасов активные саги SHALL переходить в SUSPENDED и возобновляться после восстановления сервиса БЕЗ запуска компенсаций; после восстановления команды SHALL повторяться с исходными ключами идемпотентности.

#### Scenario: Падение сервиса запасов на шаге обещания
- **WHEN** PromiseStock не может быть выполнен (сервис завершается)
- **THEN** сага SUSPENDED, компенсация не инициируется, после re-admit сервисом команда повторяется с тем же ключом

### Requirement: Проекция факта отгрузки на заказе
Система SHALL поддерживать проекции фактического доставленного количества и даты фактической отгрузки заказа на основе событий DeliveryValidated; конверсия единиц SHALL выполняться в базовую единицу продукта с округлением HALF-UP и точностью единиц количества продукта; возвраты SHALL уменьшать доставленное количество; проекция SHALL питать статус выставления счёта по факту доставки.

#### Scenario: Частичная отгрузка и возврат
- **WHEN** DeliveryValidated(qty=6) затем DeliveryValidated(qty=-2) по строке заказа qty=10
- **THEN** проекция доставленного = 4, статус счёта «к выставлению по доставке»

#### Scenario: Полное закрытие доставкой меньше заказа
- **WHEN** все документы отгрузки закрыты, факт=9 из 10 заказанных
- **THEN** строка помечена полностью доставленной по факту (закрытие без upsell-ожидания), если политика заказа это допускает
